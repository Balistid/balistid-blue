# 0006 — Anchor the record log with Tessera, cosigned by a witness on the Pi

- Status: accepted
- Date: 2026-10-01
- Decided-by: alex
- Agent: claude/opus-5.5

## Context

Root on the host can rewrite local files, so integrity needs a party off the host. The C2SP
tlog-witness protocol asks a witness to check an RFC 6962 consistency proof before cosigning; a plain
hash chain cannot produce one, a Merkle log can. Tessera v1.0.4 (transparency-dev, Apache-2.0,
2026-07-16) is a production-ready embedded Merkle log with a POSIX backend that writes C2SP tiles and
signed-note checkpoints. litewitness (FiloSottile/torchwood v0.10.0, BSD-3, 2026-09-24) is a small
witness with SQLite state and keys from ssh-agent; it is pre-1.0. The C2SP specs still change
(commits on 2026-10-01). Trillian is in maintenance mode and points to Tessera.

## Decision

1. The collector side appends one leaf per commit batch to an embedded Tessera POSIX log: the leaf
   is the SHA-256 Merkle root of the batch's record leaf hashes (ADR 0005), with first and last `seq`.
   Record bodies never enter the log (Tessera caps entries at 64 KiB).
2. Checkpoints are signed notes with Ed25519; ML-DSA-44 is revisited when litewitness supports it.
   The log origin and keys are generated by `kordon-install`, never committed.
3. The witness runs litewitness on the maintainer's Raspberry Pi, reached over WireGuard. Our process
   submits checkpoints outside the append path, so a Pi outage never blocks recording. Tessera's
   inline witness policy is not used.
4. The Pi also pulls a mirror of the tiles and sends a heartbeat. Both are our code (R9): no maintained
   tool mirrors a private tlog to a witness host; each is small and tested.
5. Versions of Tessera, torchwood and the specs are pinned; CI runs an end-to-end test host → witness.

## Alternatives considered

- Plain SHA-256 chain: no consistency proofs, so no standard witness; verification is O(n).
- Trillian: maintenance mode. immudb: BSL, a database server. Sigstore Rekor v2: a public log service.
- journald Forward Secure Sealing: the sealing key lives on the host; enabled as a second trace,
  never relied on.

## Consequences

- What we claim: after a checkpoint is cosigned, rewriting or truncating anything before it is
  detected. Records after the last cosigned checkpoint are unverified and shown as such. We do not
  claim completeness against root on the host. The Pi holds hashes only: deletion is detected,
  deleted content is not recoverable.
- Tests: a changed byte in a closed shard or a truncated shard fails verification; a forked log is
  refused by the witness; with the Pi offline, the unverified suffix is visible in `doctor` and the
  heartbeat raises an alarm within N seconds.
- The cosign interval (the window of unverified records) and N are numbers in `acceptance/0.toml`.
- A spec change in C2SP is an explicit upgrade with the end-to-end test, never a floating dependency.
