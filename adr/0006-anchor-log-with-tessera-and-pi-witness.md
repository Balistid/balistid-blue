# 0006 — Anchor the record log with Tessera, cosigned and watched from the Pi

- Status: accepted
- Date: 2026-10-01
- Decided-by: alex
- Agent: claude/opus-5.5

## Context

Root on the host can rewrite local files and fake local health, so proof and alarms must come from
off the host. C2SP tlog-witness asks a witness to check an RFC 6962 consistency proof before
cosigning; a plain hash chain cannot produce one. Tessera v1.0.4 (Apache-2.0, 2026-07-16) is an
embedded Merkle log whose POSIX backend writes C2SP tiles and signed-note checkpoints; entries are
capped at 64 KiB. litewitness (torchwood v0.10.0, BSD-3, pre-1.0) is a passive witness: it answers
checkpoint submissions and keeps the latest checkpoint per log. The C2SP specs still change.

## Decision

1. `kordon-ledger` (ADR 0007) appends to an embedded Tessera POSIX log, one entry per event, each
   with its own versioned encoding: `kordon/batch/v1` (first and last `seq`, Merkle root of the
   record leaves of one anchoring interval, ADR 0005), `kordon/seal/v1` (shard name, file SHA-256),
   `kordon/expire/v1` (shard name, seal hash) and `kordon/beat/v1` (time, health state, loss
   counters), so the tree grows when the host is idle and the Pi sees reported health. Record bodies
   never enter the log.
2. Checkpoints are signed notes with Ed25519 (ML-DSA-44 when litewitness supports it). The ledger
   holds the key and has no network; origin and keys are generated by `kordon-install`.
3. `kordon-relay` holds no key. It submits checkpoints to litewitness on the Pi over WireGuard and
   serves the tiles and closed shards read-only. Recording never waits for the Pi.
4. The Pi copies tiles and checkpoints with rsync over WireGuard (an existing tool, R9) and runs our
   watchdog: if no newly cosigned checkpoint arrives, or the tree stops growing, within N seconds,
   or the latest beat reports loss or UNKNOWN, it alerts the maintainer off the host. Root can fake a
   beat; it cannot stop the alarm for missing ones. litewitness has no such alarm: it only answers.
5. Verification runs off the host (Pi or the maintainer's machine) against the witness's latest
   checkpoint: consistency of the log, inclusion of batch, seal and expiry entries, and recomputed
   leaves from the shards the relay serves. Host-side `doctor` output is advisory only.
6. The log rolls over yearly to a new origin whose first entry is the old log's final checkpoint.
   Tiles, mirror and witness state have caps and retention in `acceptance/0.toml` (R5).
7. Tessera, torchwood and the spec versions are pinned; CI runs an end-to-end test host → witness.

## Alternatives considered

- Plain SHA-256 chain: no consistency proofs, so no standard witness. Trillian: maintenance mode.
- immudb (BSL, a server), Sigstore Rekor v2 (a public log service), Tessera's inline witness policy
  (a Pi outage would block anchoring), journald sealing (key on the host; kept only as a second trace).

## Consequences

- Claim: for anything covered by a cosigned checkpoint, a changed record, changed or missing shard,
  or a deletion without an expiry entry is detected by off-host verification. Records after the last
  cosigned checkpoint are unverified and shown as such. We do not claim completeness against root on
  the host, and the Pi holds hashes only: deleted content cannot be recovered.
- Tests: a changed byte or truncation fails verification; a forked or rolled-back log is refused by
  the witness; deletion without an expiry entry fails verification; with the Pi cut off, the
  watchdog alerts within N seconds; a relay compromise cannot sign.
- The anchoring interval, cosign interval, N and the caps are numbers in `acceptance/0.toml`.
- A C2SP spec change is an explicit upgrade with the end-to-end test, never a floating dependency.
